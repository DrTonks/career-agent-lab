# V17 结果：当前状态提交稳定了，业务验证的独立作用在提交前过滤

本轮完成 4 条新轨迹 × 4 个连续事件的三组 DeepSeek 对照：16 次共享作者执行、48 次独立复核执行，共 128 次 API 请求。任务含 64 个不同的“假设变化 × 岗位”判定，其中 18 个确实改变当前资格，46 个不改变。每组复核全部 64 个判定。

## 1. 当前状态分离修复了什么

| 指标 | text：旧摘要接口 | structured：独立当前值 | verified：独立当前值＋业务验证 |
|---|---:|---:|---:|
| 作者当前数值和岗位判定正确 | 16/16 | 16/16 | 16/16 |
| 正确当前状态提交 | 0/16 | 16/16 | 16/16 |
| 错误当前状态提交 | 0 | 0 | 0 |
| 复核后预测正确 | 64/64 | 64/64 | 64/64 |
| 正确真反例接纳 | 18/18 | 18/18 | 18/18 |
| 正确排除非反例 | 46/46 | 46/46 | 46/46 |
| 当前状态与全部预测均完成 | 0/16 | 16/16 | 16/16 |

这里的 0/16 是**旧文本接口误拒**，不是模型不会算：11 份摘要未使用旧读取器要求的“周工时=数字”格式；3 份混合多个版本数字；2 份只在历史数字前保留该格式。作者的结构化当前值全部正确。分离字段后，历史说明不必删除，当前状态也能稳定提交。这是接口可靠性收益，不应表述成推理准确率从 0% 升到 100%。

三个复核组都在每个事件主动调用相同的 `condition_check`，纠正了作者的预测错误。因此本轮复核后的正确率相同，业务验证组没有出现额外准确率增益。

## 2. 业务验证器本身是否起作用

冻结协议预先安排了“同一作者输出通过不同门控”的离线配对回放。它复用真实生成的原始预测，不新增调用、不注入人工错误，也不与复核后成绩混算。

| 同一批原始预测的处理 | 不校验业务谓词 | 校验业务谓词 |
|---|---:|---:|
| 正确原始预测保留 | 61/61 | 61/61 |
| 错误预测进入已解决列表 | 3/3 | 0/3 |
| 接纳预测中正确项占比 | 61/64（95.3%） | 61/61（100%） |
| 已解决预测覆盖率 | 64/64 | 61/64（95.3%） |
| 正确真反例召回 | 17/18 | 17/18 |
| 程序标记整个事件完成 | 16/16 | 15/16 |

三个错误全部来自同一事件，样本集中。验证器拦截错误后保留待解决状态，没有凭拒绝动作制造正确答案，也没有多检出原先漏掉的真反例。其明确作用是：**让“模型写出了一个反例”与“这个反例已经得到验证”成为两种不同状态。**

具体例子：便民服务场景初始出勤为周一 7 小时、周三 7 小时、周五 4.5 小时。B 岗要求至少两天各达到 4 小时。作者误判“周三全部占用后，B 岗不符”；事实上周一与周五仍达标。另两项错误是 A 岗对周五减少一小时、周三全部占用的预测。验证器分别重算同一规则下变化前后的判定，三项均未通过；普通复核读取同一工具回执后也全部纠正。

## 3. 对方案的影响

保留反例取证与持续复核的方向，核心实现进一步明确为：**把当前声明与历史解释分离，把模型对条件变化的预测转成绑定事实版本和规则版本的可检验任务，再分别记录当前状态提交与预测解决。**

本轮支持“减少文本接口误拒”和“提交前阻止错误预测成为已验证记忆”两项收益。当前完整复核已经能纠错，后续最值得检验的是：在原生多智能体流程中，只为未通过校验的局部任务补充复核，是否能在维持正确率的同时减少重复取证与整套重跑。无需仅为争取准确率差距继续扩大量化相同任务。

本轮是两种代理的组件对照；生产原型已经支持字段传递、存储及证据权限校验，业务门控在本轮实验驱动器中运行。岗位条件使用公开的结构化时间规则；假设场景预先给定，本轮测预测与校验，不测规则自动编译或自由生成探针。

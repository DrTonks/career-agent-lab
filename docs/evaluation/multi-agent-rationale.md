# 为什么采用多智能体

我们选择多智能体，是因为职业规划需要持续维护用户事实、岗位条件、成长路径和报告，不只是生成一次回答。总控负责依赖与状态，四个专家分别处理自己的知识、工具和工作历史，通过带来源的结构化产物协作。这样可以追踪建议依据，在条件变化时使相关结论失效，并在任务内保留不受影响的工作。当前观察到输入消耗更低，部分画像与综合规划表现更好；主要价值仍是可控、可追踪、可维护的业务执行过程。

## 可以明确说明的工程优势

| 优势 | 当前实现 | 业务价值 |
| --- | --- | --- |
| 职责和上下文边界清晰 | 画像、匹配、路径、报告分别持有消息历史、专业指令、工具与知识视图；私有探索历史不自动广播 | 避免每一步都携带全部过程，便于单独调整专家策略和定位问题 |
| 交接可追踪 | 产物包含来源、结果、未知项与后续动作，接收者按权限读取详情 | 能解释“这条建议由哪个步骤、哪些材料支持”，而不是只得到一段最终文本 |
| 支持变化与局部恢复 | 总控管理依赖、尝试和失效传播；任务内保留不受影响的产物，持久化 checkpoint、审批和回执 | 条件变化或局部失败有明确影响范围，不必将整个流程视为一次不可检查的生成；跨用户新输入仍按版本保守重验 |
| 专业任务有明确契约 | 画像区分未知与缺失；匹配由代码检查硬条件；路径校验真实图边；报告综合授权产物 | 专家不仅是角色提示词，还承担可检验的输入、工具和产出责任 |

实现入口：[运行时](../../src/runtime.ts)、[协调与失效](../../src/coordination.ts)、[工具](../../src/tools.ts)、[持久化](../../src/storage.ts)。恢复与失效已有[协调测试](../../tests/coordination.test.ts)和[真实进程故障测试](../../tests/process.test.ts)。这是运行时机制的工程证据，不等于所有业务回答已稳定通过验收。

## 已有数据支持的收益

以下质量数据来自本地全量会话AI评分：24个场景、48份会话，按整段会话配对，五维0–4分。只公开摘要，原始评分与逐句证据保留在本地 本地评审目录。

| 论据 | 观察结果 | 合适的表述 |
| --- | --- | --- |
| 输入消耗降低 | 原执行中22个完整无中断配对，总输入少 **10.15%**，费用估算少 **3.45%** | 当前配置下观察到资源节省；不是等质量、任意任务下的保证 |
| 事实与一致性略有改善 | 14个双方内容可评的场景对：事实支持 **3.21对3.00**，一致性 **3.00对2.79** | 部分交付更谨慎地处理事实和跨轮口径，尚不能断言由隔离单独造成 |
| 画像与综合规划有较好案例 | 有证据画像的事实/一致性为 **4/4对3/3**；完整后端规划五维为 **4/4/4/4/4对3/4/4/3/3** | 能展示多专业产物组合后的实际回答，而不只展示架构图 |
| 部分更正场景更完整 | 城市更正完整性 **3对2**、一致性 **2对1**；八轮故事一致性 **3对2** | 观察到局部多轮收益，适合作为案例，不能推广为长会话稳定胜出 |

表中质量分数按multi-agent、skills顺序排列。未发布回复的事实等维度记为未评，其交付缺失仍计入完整性；因此14对质量均值不能代替全部24对的可靠交付率。评分来自一个独立上下文AI子agent，人工分数尚未保存；同一评分者连续阅读，且一处控制材料暴露了匿名A/B状态，不能称为严格完全盲评。各维度描述性区间均包含零，当前结论是局部收益，而非全面胜出。

资源的来源与口径见[最终统计](results.md)。输入下降未同比转化为费用下降，是因为缓存命中率较低、输出更多，且最终核验抵消了部分专家阶段收益。

## 分数较低的原因与改进方向

| 现象 | 已知原因或证据 | 优先改进 |
| --- | --- | --- |
| 完整性两边均为 **2.63/4**（24对） | 两边各有11轮答复暂扣；部分任务已有内部产物，但用户没有收到实质答复。已复现数量核验将“12个能力维度”等误识别为检索计数的问题，但不是所有暂扣均已归因 | 修复数量/语义范围误拦，明确已核实内容的部分交付规则；保留真正无依据内容的拦截 |
| 可执行性为 **2.48对2.39**（23对） | 未交付按0分保留；部分已交付建议缺少时间安排、验证条件或下一步细节 | 同时提高实际交付率与行动计划的具体程度，不靠补足篇幅提分 |
| 多轮一致性仍有缺口 | 两侧都出现已更正事实重新被当作未知、事实/估计混用、审批状态口径变化 | 核查当前有效事实与版本的读取、综合和引用，不把所有问题笼统归为上下文长度 |
| 总活动耗时略高 **3.21%**（22对） | 原执行中调用多1.31%、输出多3.50%；隔离需要重读和交接，最终核验也有开销，尚未拆出各环节的因果贡献 | 依据阶段日志减少重复读取和核验，保留必要的证据检查 |

数量范围问题已由本地离线反例复现，历史诊断留本地。这些是局部修复入口；目前没有证据要求重写总控与四专家架构，也不能预先保证修复后所有低分消失。

## 为什么不直接用四个skills

**四个skills可以实现相近业务。** 当前强skills基线使用同源专业指令、相同工具、权限控制和记忆机制；专业知识与安全能力并非multi-agent独占。核心差别是：multi-agent将每一步的工作历史、状态和交接显式分开，skills基线持续携带规划、技能执行与综合历史。

简历润色或单次检索通常用skills即可；需要多个领域产物、持续更正、审计和恢复时，独立专家边界更便于组织与维护。skills也可以放进专家内部，两者并不排斥。工程机制已经实现，业务上的净收益仍要结合场景判断：完整性24对中两边各高6个、相同12个；若干岗位筛选与转岗场景skills交付更好。

当前真实运行覆盖的是总控调度与结构化产物交接，两侧主动 `collaboration_request` 均未触发。因此可讲“可追踪的专家工作流”，暂不把“自主讨论或涌现协作”作为已验证优势。

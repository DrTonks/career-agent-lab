# 上下文与已完成检索工作

专家工作状态由消息、已读证据、checkpoint及工具缓存组成。multi-agent每次专家尝试拥有独立线程；skills沿用连续历史。两者调用同一压缩函数和领域工具。完整请求与工具结果仍保留在运行数据库，模型当前看到的消息是其中受容量限制的视图。

总控规划另有[进度与收尾机制](../../src/planning-progress.ts)：新目录查询或新增原文覆盖推进规划，连续三轮未推进或最后规划轮只提供plan_submit。详细证据审核委派给专家，不能借此省略任务。历史压缩摘要只提示需要逐字引用时重读，不要求为了提交计划反复读完相同材料。该机制不改变专家权限、原文保存或引用要求。

## 保留规则

[runtime.ts](../../src/runtime.ts)的`compactMessages`保留系统消息、原始用户消息、当前TASK_DATA、最新完整工具调用/结果组，以及当前授权依赖版本仍需使用的已读页面。不能为了压缩截断工具调用对，也不能将旧版本依赖替代当前版本。

被移除的知识原文使用有限摘要和原文读取入口。检索计算结果另外由[working-set.ts](../../src/working-set.ts)形成`WORKING_SET_V1`：

| 工具 | 保留的工作结果 |
| --- | --- |
| categories_search | 类别ID、证据ID和版本 |
| jobs_search | 实际候选/未知候选ID、筛选总数、类别覆盖、约束版本与数据范围 |
| jobs_check | eligible、逐项检查、违规/未知条件、技能交集及缺口 |
| graph_paths | 实际返回的节点、成本、图边证据ID和模式 |

每条还保存原工具参数、参数键和完整结果hash，可对照原始调用。只投影已返回的字段，不重新推断候选资格或图边；失败、无效JSON和非适用工具不成为已完成检索记录。画像评分与报告草稿不走这一投影，仍按自身工具和来源协议处理。

工作摘要是任务数据，不是系统指令或个人事实来源。它不更新已读证据集合，不扩大工具权限；再次读取仍由正常授权、版本及原文校验控制。需要被省略的细节时，可以重新调用记录中的工具和参数，符合相同执行身份的调用由现有缓存重放。

## 有界选择与任务隔离

工作摘要最多16条；容量上界为6000估计token、消息可用上限的一半及剩余空间三者的最小值，计入原来的上下文与累计运行限制。不是额外额度。记录按完整JSON保留或省略，类别覆盖最多展示10项，显式附带原返回数量与省略数量。省略不表示没有结果，筛选计数不表示市场规模。`omittedReceiptCount`累计记录省略次数，不是独立模型调用数。

优先保留已找到路径、确定性岗位检查，再保留检索入口；每类工具先保留一条，再考虑其他变体。有目标且已找到的路径优先于后续空查询，避免“目标类别没有后继”覆盖“到目标类别已有路径”。至少一份已发现路径也容纳不下时，继续移除可压缩历史；仍放不下则使用原有软目标到硬上限的回退。硬上限或运行剩余量不足时明确失败，不悄悄删除全部路径发现。

摘要绑定当前TASK_DATA的hash。切换专家任务、尝试或约束后的新激活不会继承旧任务摘要。skills既有连续历史的保留规则不变；这些摘要不能使已失效产物变成当前证据。源数据和约束在单次运行内固定，重新运行仍使用新的快照身份。

## 验证边界

### 三种不同的容量

代码缺省单次请求硬上限为48000估计token，专家软目标为22000；估计器使用UTF-8字节数/2向上取整，是保守预检值，不是供应商实际token数。工具定义也占用请求容量。上述数值是本项目配置，不能当作模型供应商的上下文上限。

可复用的[full-task配置](../../evals/configs/full-task.json)提供较大的单次与累计容量；具体参数以该文件为准。容量调整不改变知识权限、压缩规则和恢复身份。

审核来源选择另有容量目标。最终消息还含片段目录、计算事实、系统提示与工具定义，因此必须继续检查整体单次容量；增大来源目标不保证字段和查询范围选择正确。

专家模型/工具轮数由CAREER_MAX_EXPERT_TURNS配置，代码缺省10、当前full-task为20。专家LangGraph递归上限随轮数调整，避免仅增加外部配置后仍被旧的40节点限制截断。每个模型轮次可能含多个工具调用，这个值不是工具总数；累计调用/输入/输出及超时仍独立生效。两架构确定性测试执行21轮分页读取后提交，并验证低轮数配置仍产生expert_turn_limit。

单任务另有累计输入、输出、调用次数与时限，并为最终综合和核验保留容量。多次发送相同历史仍累计计入输入，压缩不能扣回已发送的输入；最终阶段释放预留也不保证一定足以完成所有审核窗口。

当运行剩余量小于单次上限时，下一请求还必须装进剩余量。必需消息、工具定义与受保护依赖页无法容纳时，运行时在发送前报run_limit。实际usage与本地估计用于保守准入，诊断分别展示，不能把估计写成精确分词数。

### 任务内压缩与跨用户轮次

现有压缩是确定性投影和裁剪，没有模型生成的递归会话摘要。CONTEXT_DIGEST保留被裁剪原文的短摘录和ID；每项最多取700字符，拼接后最多保留末尾3000字符，因此它有损，甚至可能从记录中间截断，不能当成完整结构化事实表。WORKING_SET_V1则保留完整JSON计算记录及省略标记；被裁剪的其他推理文本不会自动转成可靠事实。

reply创建新输入版本与子任务，简历和约束可显式替换。当前v2续接只把本轮请求直接放入任务，历史陈述按授权祖先链持久保存并分页读取，不再把所有轮次文本不断拼接进本轮请求。旧v1记录兼容读取；单次输入仍受schema限制。详见[原始输入与历史工具](input-history.md)。问题解决记录、批准记忆与checkpoint不能替代完整原文。

现有测试覆盖连续两次压缩、依赖页/工具对完整性、任务切换、记忆生命周期与两轮reply；尚未完成反复压缩后的长会话业务验收。业务观察见[最终观察与边界](../evaluation/results.md)。

### 当前执行状态视图（execution-state-v1）

协议反馈回归出现了在同一尝试内重复使用旧expectedVersion的现象。现在DomainTools从SQLite实际记录生成执行视图：executionId/attempt、输入与约束版本及哈希、授权依赖版本、每个问题的版本/状态/剩余项/声明数量和记录哈希、输入读取覆盖，以及本次尝试最新评分回执的身份和分值。不复制整份声明和引文；完整追问记录可通过clarification_update的空updates只读返回，原文仍按已有工具读取。

该视图是代码生成的执行状态，不是个人事实或可直接引用的原文。只显示本角色/本次尝试的权限范围；失败尝试保留为历史，不能混入当前版本。两种架构使用相同状态规则，skills仍保留连续历史，不借此变为四个独立上下文。

Runtime先按不含旧状态视图的逻辑调用身份查找已接收响应；命中时复用原messages，不读取当前数据库来重算视图。新调用才生成executionState与executionStateHash，保存到模型调用记录，并以EXECUTION_STATE消息固定在当前TASK_DATA后。压缩不会删除它，也不会截断必需状态；无法容纳时使用已有容量回退/明确错误。两边共用此规则，每个新调用替换上次视图，技能历史仍连续。

profile_score成功后按调用身份追加持久化回执，最新有效回执决定提交分值；恢复时校验结果哈希、工具参数缓存键和评分版本。新评分、新尝试与原尝试明确区分；普通工具文本中的同名scores字段不能更新当前评分。评分观察的语义正确性仍须审核。画像引文失败返回具体observations或artifact.evidence字段位置与实际可用的读取提示，不回滚此前成功的追问。

测试入口是[execution-state.test.ts](../../tests/execution-state.test.ts)：30问题局部更新、过期命令、跨角色/尝试隔离、评分重算、伪评分忽略、八次压缩和两架构真实进程丢失后的原快照复用。进程测试直接针对Runtime模型持久化边界，图checkpoint恢复仍由既有process测试覆盖；这不是八轮真实业务对话验收。新增视图改善模型行为的程度仍待真实回归，不能用确定性测试宣称已消除循环。

[working-set.test.ts](../../tests/working-set.test.ts)检查跨两次压缩、任务切换、零/未知候选、完整JSON和省略计数、失败过滤，以及已发现路线不被后续空查询替代。既有容量测试继续检查工具对和多页依赖保留。

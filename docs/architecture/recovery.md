# 执行恢复与故障窗口

恢复依赖 SQLite 中的已提交记录，不能根据某个请求“应该已经完成”推断结果。每次恢复先检查用户、约束、记忆、实现、提示词、模型与检索指纹，再取得可续期的独占租约。取消、失效或旧执行者不能继续写有效产物。记忆审批细节见 [记忆生命周期](memory-lifecycle.md)。

## 模型响应回执

每个模型请求保存执行位置 scope 和完整请求哈希：规划修正轮次、专家尝试/轮次、协调请求/轮次或最终综合，以及角色、模型、模式、实际消息、工具 schema 和流式设置。相同文本出现在另一专家尝试或轮次，不会误复用上一轮响应。

完整响应在检查当前上下文与执行租约的 SQLite 事务中保存，随后状态图才能继续。若在响应落库后、图 checkpoint 前退出，同一请求恢复时读取已完成响应，记录 `model.recovered`，不再请求供应商、不新增调用行，也不再次累加 usage。只有完整 stop/tool_calls 响应可复用；截断、失败或参数不一致的记录不可作为成功回执。

请求已开始但未持久化完整响应时，恢复将原调用标为 `interrupted`，`outcomeUnknown=true`、usage=null，并在运行限制内重新请求。供应商可能已经处理过原请求，因此无法保证供应商端恰好执行一次。原调用仍占调用次数，未知 token 用量按预留量检查运行上限；统计总量保持 null，不伪装成零。应用已收到但因取消/失效拒绝的响应仍留作审计，不进入可恢复成功结果。

## 流式中断留痕

CompatibleProvider 将正文、工具 ID/名称/参数增量、已收到的 usage、结束原因和 DONE 标记规范化为有序片段；Runtime 在 `model.stream` 事件中逐片段同步落库。隐藏思考、授权头、任意供应商元数据不进入该记录，无法解析的原始字节也不作为正文保存。模型适配器或装饰器必须透传 `complete` 的第五个 progress 回调。

正常完成需同时收到结束原因与 DONE。断流、坏 JSON 或缺失结束标记会保留 `partialResponse`、`partialFinishReason`、已知 usage 和片段数量，返回失败；不完整工具参数不能执行。记录器写入失败时停止请求，不悄悄丢弃记录后继续执行。收到响应前的连接失败可有界重试，用户取消不自动重试。

进程在片段提交后退出，恢复由持久事件重建部分响应并将原调用标为中断，不把部分输出提升成成功回执。统计使用实际到达的 usage，未到达则为 null；片段数和序列化 payload 字节数单列，后者不是 SQLite 文件占用。记录只保证已落库片段：网络接收与落库之间退出仍可能有无法确认的间隙，历史记录不事后补造。

## 工具与产物恢复

工具缓存键包含执行尝试、角色、工具名和规范化参数。缓存命中仍检查当前运行；恢复重建已读证据记录。记忆提议 ID 由请求、来源尝试和内容确定，报告草稿 ID 由内容确定。副作用已提交但返回缓存尚未提交时，重复执行这些本地操作不会产生第二条等价记录。当前工具不包含邮件、支付或外部写入；未来加入时必须单独设计外部幂等协议，不能直接沿用这里的承诺。

专家完成的 checkpoint 可恢复为产物；产物已保存时优先复用持久产物。协调修订与失效传播有事务回执，恢复不会再次失效刚生成的新产物。审批回执和记忆写入也在同一事务中。

## 已验证的实际退出窗口

`tests/process.test.ts` 由独立子进程执行并在指定边界实际 SIGKILL，恢复等待租约到期。所有模型调用均为明确的测试回放。

| 窗口 | 两架构覆盖 | 核验的不变量 |
| --- | --- | --- |
| 完整响应保存前 | 是 | 原请求结果未知；重发留痕，未知 usage 不补造 |
| 完整响应保存后、模型节点返回前 | 是 | 复用回执，无额外模型调用或重复 usage |
| 流式片段提交后、完整响应前 | 是 | 重建部分正文/工具参数，禁止执行不完整工具调用 |
| 记忆提议事务前/后 | 是 | 提议最多一条，未批准时不是长期事实 |
| 工具返回缓存写入前/后 | 是 | 缓存或幂等副作用恢复，提议不重复 |
| 专家产物保存前/后 | 是 | 已完成专家不重新调用模型 |
| 协调事务后、根图 checkpoint 前 | 是 | 修订只提交一次，新产物不再次失效 |
| 审批事务前/后 | 当前覆盖共享持久化路径 | 显式审批，记忆版本只递增一次 |
| 活跃进程与旧所有者竞争 | 当前覆盖共享租约路径 | 排他执行，旧 owner 不可写产物/checkpoint |

其他集成测试覆盖取消期间模型返回、检索阻塞后取消、审批拒绝、过期、约束变化和事务回滚。迟到检索结果不能新增工具返回缓存或产物。上述有限窗口不是所有操作时刻的穷尽证明；其他 checkpoint 写入窗口、跨进程取消竞争和长期多轮业务仍需进一步验证。当前门槛状态见 [开发与验证](../development/contributing.md)。

## 验证证据与复现

执行记录保留原始调用、恢复事件、checkpoint和失败，不因为恢复成功删除中断记录。runMetrics分别报告recoveredModelReplies、interruptedModelCalls、unknownUsageCalls，恢复次数不是新模型调用数。

流式协议与Runtime持久化测试覆盖片段提交后的真实进程终止和检索期间取消。协议回放模拟HTTP流，不调用模型供应商，也不证明业务语义正确。

恢复入口会核对本 run 的全部遗留 started 调用，包括后续计划不再经过的位置；不能只在相同请求重发时处理。有效流前缀和已观察 usage 保留，损坏序号记录 reconstructionError，原始坏帧不删除。相关回放见 stream-runtime.test.ts。

最终综合接收每个步骤的 failure、stepId、attempt 及实际协调轮数。不可重试的资源/永久错误与协调轮数耗尽分别诊断；不能因为产物 partial 就自行推断失败原因。


## 完整响应中的无效工具 JSON

流式未完成的参数仍不执行。对于已经完整收到、但JSON.parse失败的工具参数，总控保存`tool.arguments_rejected`事件及幂等缓存，回传解析错误、参数哈希、相同响应次数和明确纠正指令；原参数保留在model_calls，不自动补括号或构造业务字段。

同一步骤尝试中，相同工具名和完全相同参数的第三次完整响应触发`model_protocol`，不重跑整位专家。此前两次提供纠正机会，成功修正后可以正常执行。计数依据持久化的完整模型响应作用域，恢复不会因内存清空重新获得无限机会；不同参数仍受原专家轮数/运行总限制。此机制目前只处理语法错误，不将所有业务校验失败等同于协议错误。

失败记录按执行位置和工具调用ID在同一事务写入；被拒参数从未进入DomainTools。metrics新增toolArgumentFailures，区别于已进入工具执行器的toolFailures。完成结果之后，同批多余工具不会执行，也不能因其无效参数撤销已完成结果。

对应进程证据：tool-protocol.test.ts在两架构无效响应完成后、拒绝反馈事务完成后实际SIGKILL，恢复均只新增两次专家调用且拒绝事件不重复。这验证持久化与界限，不验证真实模型一定接受纠正。

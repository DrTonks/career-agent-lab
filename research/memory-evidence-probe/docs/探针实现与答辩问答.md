# 长期记忆探针实现与答辩问答

本文用于回答“模型的潜在能力是什么、探针具体是什么、和普通复核有何区别、实验说明了什么”。两页方案讲主线，这份问答保留实现细节。当前方案名称为“基于反例取证与持续复核的长期记忆探针”。

## 一 先把核心想法说清楚

### 1 能用半分钟介绍吗

我想发掘大模型把自己的结论转化为可检验问题的能力：模型不仅给出岗位推荐，还指出哪些条件变化可能使推荐失效、应该查看什么证据。我把这些问题保存为绑定来源、版本和责任角色的探针任务。新信息到达后，系统取证、演练条件变化，并安排受影响角色复核。最近的改进把当前结论与历史解释分开，并验证“条件变化是否真的改变业务判定”，避免把一个听起来合理的假设直接当成已验证记忆。

### 2 什么是探针 为什么这样命名

它是附着于目标结论的定向检测任务：指定检查哪个条件、观察什么证据、由谁处理，以及怎样判断任务完成。“探针”强调主动提出可检验的问题并等待反馈。它不是网络探测工具，也不是给记忆加一句“以后注意检查”。

### 3 探针到底是一段 JSON 还是一个对象

两者是不同层面的说法。程序执行时，任务是 JavaScript 对象；模型通过工具调用输出 JSON 参数；保存与跨轮恢复时，对象被序列化为 JSON。真正的机制还包含触发、取证、版本校验、角色调度和状态更新，单独保存一段 JSON 不会自动工作。

当前实现不是一个囊括所有内容的 `Probe` 大对象，而是相关联的数据：持续任务、来源与计算回执、专家产物，以及本轮新增的当前声明和业务预测校验结果。不同实验版本的字段不能拼接后冒充同一个已经运行的接口。

### 4 和普通复核有什么区别

| 环节 | 普通复核的一般做法 | 本方案增加的约束 |
|---|---|---|
| 检查对象 | 重新检查当前答案 | 绑定具体旧结论及其适用条件 |
| 触发 | 用户要求或固定增加一次复查 | 结合相关事件、来源版本和未解决任务判断是否派发 |
| 取证 | 本次临时查资料 | 保存待查来源与读取回执，区分已读和仍待核定 |
| 演练 | 可使用反例，但未必保存结果 | 明确假设、规则版本和变化前后判定，核验是否真的推翻结论 |
| 完成 | 回答或提交结束 | 分开记录执行、当前声明提交和问题是否解决 |
| 后续 | 依赖再次读取历史 | 未解决任务独立保存，相关变化后继续处理 |

普通复核也可以拥有上述能力；差异取决于具体流程，不是名称。实验给普通复核相同工具，允许它自发使用反例。本轮充分取证后，各组预测都正确，不能把共同收益归给显式反例步骤。

## 二 数据结构与模型分工

### 5 原生多智能体实验的任务长什么样

V16 的 `review_submit` 由模型提出任务，`validateTask` 和 `reconcile` 补齐身份、版本与状态。下面是字段示意，ID和版本用短值帮助阅读：

```json
{
  "subject": "user",
  "field": "availability.weeklyHours",
  "question": "排班变化后，旧岗位结论是否仍成立？",
  "targets": ["match", "path", "report"],
  "claimRefs": ["artifact:run-1:match"],
  "evidenceRefs": ["job:b"],
  "readIds": ["job:b"],
  "action": "dispatch",
  "eventQuote": "周三新增课程",
  "branches": [{"condition": "可出勤时间减少", "consequence": "需要重新核定资格"}],
  "key": "由subject与field计算的任务键",
  "watchedIds": ["job:b"],
  "sourceVersions": {"job:b": "来源内容哈希"},
  "binding": {"claimRefs": ["artifact:run-1:match"], "sourceVersions": {"job:b": "来源内容哈希"}},
  "notFact": true,
  "status": "ready"
}
```

模型填写问题、目标角色、引用、拟读取资料、事件原话和假设分支；程序计算任务键，检查引用是否可见，绑定来源版本，并维护状态。实际对象还可包含 `activation`、`lastExecution`、`resolution`。完整真实实例保存在 [V16 原始复查记录](../../../evals/advice-repair-v16/results/test-r2/events/v16-overlap/counterexample/event-1/review.json)。

注意：V16 的 `binding` 绑定产物引用和来源版本，没有本轮新增的独立 `ruleVersion` 预测字段。不能说所有版本都已经统一采用同一种绑定结构。

### 6 本轮增加的结构是什么

V17 增加 `currentAssessment`，它是当前声明，不是探针任务本身。下例为一个岗位的结构示意；完整提交须覆盖当次全部岗位：

```json
{
  "schemaVersion": "current-assessment-v1",
  "factsVersion": "当前事实哈希",
  "weeklyHours": 17.5,
  "judgments": [{"jobId": "b", "ruleVersion": "规则哈希", "verdict": "符合"}],
  "evidenceIds": ["event:1", "job:b"]
}
```

单条预测另存为：

```json
{
  "hypothesisId": "friday-minus-one-hour",
  "jobId": "b",
  "factsVersion": "当前事实哈希",
  "ruleVersion": "规则哈希",
  "predictedAfter": "符合",
  "claimsRefutation": false
}
```

`hypothesisId` 引用独立的假设原表；验证器在副本中演练并输出 `before`、`after`、`changesDecision`、`valid` 和 `status`。任务门控再记录 `currentStateCommitted`、`acceptedCases`、`unresolvedCases`、`fullyResolved`。这些对象共同表达“当前怎么判断、模型预测什么、哪些预测已验证”。

真实输出：[作者结果](../../../evals/advice-repair-v17/results/test-r1/v17-service/event-1/author/actor-result.json)；[验证组结果](../../../evals/advice-repair-v17/results/test-r1/v17-service/event-1/verified/result.json)。

### 7 哪些部分需要大模型 哪些由代码负责

模型负责从上下文提出问题、选择待查材料、表达条件变化的影响，并进行业务解释。程序负责结构检查、可见来源校验、版本绑定、权限、调度和确定性运算。V17 时间规则直接以公开结构化卡提供，代码计算工时与规则判定；这轮主要测预测和验证接口，假设场景预先给定，没有测模型自由生成新假设的能力。

### 8 模型写出 JSON 就算反例成立吗

不算。格式正确只能说明字段合法。验证还要检查：引用是否真实可见、规则和事实版本是否一致、预测是否符合演练结果，以及结果是否真的相对当前判定发生改变。V16 已处理来源和版本问题；V17 为支持的时间规则补充了最后的业务判定验证。

### 9 它会自动预测未来发生什么吗

这里的演练回答“如果条件变成这样，结论会怎样”，不预测该变化一定发生。假设在副本中计算，真实状态只依据实际观测更新。“明天可能加课”不会直接改成“已经加课”。

## 三 在一轮上下文里怎样运行

### 10 一次完整处理经过哪些步骤

原生任务链为：新事件到达 → 加载相关旧产物、持续任务和来源目录 → 复查代理提出或激活任务 → 程序检查引用与版本 → 总控分派相关专家 → 专家读取授权原件并提交产物 → 记录执行与关闭结果 → 保存待办。

本轮新增组件在提交环节进一步分离当前值与历史解释，并核验假设是否改变业务规则的判定。该组件已完成独立实验；接回原生四专家的完整新闭环是下一步。

### 11 探针会怎样出现在提示词中

V16 复查代理看到 `event`、`conclusions`、`sources`、`catalog`、`pendingTasks` 和已有回执。总控接收 `reviewContext`；`expertReviewContext` 按 `targets` 过滤，专家只看到与自身职责相关的任务及历史结论。当前实现中目录与派生检查可以共享，实际原件访问仍受领域工具权限限制。

派发给执行专家的问题被渲染成中立核查请求，原始模型假设留在审计记录，避免未经核验的候选数字被暗示成答案。任务、历史结论和已读证据在上下文中分区表达；模型不能因为任务里有一个来源 ID，就获得该来源的读取权限。

V17 组件复核者另外看到 `stateProjection`：文本组接收摘要，结构化组接收 `currentAssessment`。三组都有相同原始来源、作者预测及 `condition_check` 工具。

### 12 用实习时间变化举例

初始周一7小时、周三7小时、周五4.5小时，B岗要求至少两天各达到4小时。记忆认为符合；探针关注能否继续满足这个计数条件。

若周五被占用一小时，周五变3.5小时，但周一和周三仍达标，B岗结论不变。这个变化不是B岗的有效反例。若在该状态下周三也只剩3小时，就只剩周一达标，B岗转为不符。系统应根据真实排班取证，再让匹配、路径和报告角色检查相关产物。

这解释了本轮的关键改进：不能只检查某一天变少了，还必须检查变化是否足以改变整个规则的判定。对“能实习3至4个月、岗位要求改成6个月”的情况，也先核实新要求及作用范围，再更新受影响结论。

### 13 为什么任务完成要分开记

“资料读到了”“专家提交了”“问题解决了”是不同事件。读到资料可能仍缺关键值；专家可能提交待核定状态；当前判断已正确，也可能仍有一个反例预测未通过校验。本轮允许当前状态提交，同时把错误预测留在 `unresolvedCases`，不要求把一切压成一个完成标志。

### 14 重复追问与上下文压缩怎么办

V16 用主体与字段生成稳定任务键，结合来源版本、事件原话和已有执行记录，减少无变化时重复派发。没有新证据时可留在等待状态。该规则减少重复，不保证消除一切语义重复；同一字段关联多个岗位时也需要注意粒度。

跨轮任务和版本状态独立序列化，不依赖聊天摘要记住待办。早期实验测试过状态恢复与历史截断；V17 没有新增压缩消融。压缩后仍需装载相关任务，并重新读取当前有权限的原件；仅有任务哈希不能恢复丢失的证据正文。

### 15 它和多智能体有什么关系

主要作用于任务分派、证据交接和完成判定：把一个条件变化关联到受影响角色，共享可追溯回执，再检查各角色是否更新了自己的结论。画像维护个人约束，匹配判断资格，路径调整计划，报告统一对外表达。版本绑定用于识别新旧产物混用，权限检查避免把别的角色的旧引用直接当作自己的新证据。

早期是同一模型顺序承担三类角色；V16 使用原生总控与独立专家上下文，共2次共享初始运行、18次后续业务运行；V17 是记忆作者与复核者的双代理组件对照。多智能体不要求不同厂商模型，关键是职责、上下文、工具权限和交接机制独立。

## 四 如何解释原创性和实验

### 16 你发现了大模型的哪一种潜在能力

我关注的是“把自己的结论转化为可检验问题”：模型能从推荐理由中提出值得查证的失效条件，把模糊怀疑转成证据需求。通过任务状态和工具反馈，这种能力可以用于维护旧结论，而不只用于当场回答。模型提出问题、工具验证、真实证据更新三者的分工，是我动手实现和检验的重点。

### 17 原创思考体现在哪里

我的设计切口是把结论的适用边界变成可跨轮续办的任务，并将假设与事实、当前声明与历史说明、提交与解决分开管理。最新细节是检查“变化是否真的改变绑定规则的判定”，而不凭来源真实或角色意见一致就关闭任务。原创性主张是针对这一组合流程及具体实现；JSON、反事实推理、版本管理和复核本身都有已有研究。

### 18 与已有产品怎样比较才准确

Hindsight公开提供记忆滞后信号并引导回查事实；Letta提供持久与共享记忆、Git版本和后台整理；Graphiti提供时序事实、失效处理及来源追溯。本项目侧重把目标结论的失效条件组织成取证与复核任务，并验证候选反例是否改变规则判定。可以叠加在这些记忆基础设施上，不能把产品没有介绍某项功能写成绝对不支持。官方链接见[产品与研究资料](产品与研究资料.md)。

### 19 哪些实验结果最值得讲

早期双模型实验：保持自由探针不变，澄清状态动作协议后，DeepSeek与GPT主评审严格通过数分别从2/54到29/54、13/54到43/54。连续事件实验：探针完整正确数64/72，普通流程52/72；额外复核66/72，探针比其少21次角色调用、总token少6.3%。这里是整个流程的比较。

本轮16个共享作者当前判断全部正确。结构化当前值使16个正确状态均成功提交，旧摘要读取器误拒16个；这是接口可靠性修复。复核后三组预测均64/64正确。对作者原始64个预测做离线配对回放，验证器拦截3个错误、保留全部61个正确预测。错误来自同一个事件，不能把64项都当成独立轨迹。

### 20 是否单独证明了反例步骤优于普通复核

还没有建立稳定的独立最终正确率优势。早期四组拆分实验中，显式分支与持续任务的平均效应较小；本轮普通复核借助同样工具，也修正了作者错误。已确认的作用是闭环可执行、当前提交更稳定，以及把未经验证的预测挡在“已解决”状态之外。下一步应检验局部复核是否减少重复工作。

### 21 过滤三个错误是不是就等于修好了三个错误

不是。原始预测配对回放中，验证器接纳61项、留下3项待解决，未自动补出正确预测。真实复核阶段三组都读取工具回执，才把64项全部判断正确。拦截与纠正、回放与实时实验应分别表述。

### 22 规则都能写代码 那还要模型做什么

本轮选择可执行时间规则，是为了能独立核查“反例是否成立”。复杂语义任务仍需要模型识别依赖、提出问题、选择证据和解释影响。代码能算时间，不会自动知道职业报告里哪条结论值得持续维护。更一般的规则翻译还需单独验证，不能直接从时间规则推广到所有领域。

### 23 总费用与调用量如何回答

本轮128次DeepSeek请求：共享作者32次、三组复核各32次。供应商记录输入402,654、输出59,255 token；缓存输入189,180已包含在输入总量里。共16次作者和48次复核执行，每次均先用工具再提交。具体费用以账户账单为准，未把缓存token重复加总。

### 24 下一步为什么不是继续无限扩大样本

当前普通复核已达到本轮任务的正确率上限，再增加同类样本未必能定位独立收益。更明确的实验是把业务校验接回原生多智能体：比较“每次全量复核”和“只对未通过校验的任务局部复核”，预先固定资料权限与调用上限，检查正确率、遗漏更新、重复取证、角色调用和token。也要加入规则版本变化、证据缺失和过期产物场景。

## 五 现场演示顺序与用词

先展示初始排班和B岗规则，再展示“周五少一小时”的假设；让老师看到条件虽变而判定不变。随后展示进一步占用周三，说明此时才会改变资格。最后打开任务对象、当前声明和验证结果：哪些字段由模型提出，哪些来自程序计算，哪些是待核定状态，一目了然。

推荐说：“当前声明提交更稳定”“错误预测没有进入已解决记忆”“反例用于指导取证，真实证据用于更新事实”。不要说：“能够预测未来事实”“探针全面超过普通复核”“16项误拒等于16项推理错误”“本轮完成了四专家新版闭环”。

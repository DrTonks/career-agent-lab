# 记忆探针：读者常见问题与答辩要点

**面向多角色智能体的长期记忆主动复核方案**

本页按“概念—实现—实验—后续工作”整理常见问题。方案总览见 [README](../README.md)，可运行实现见 [runtime](../runtime/)，完整对照数据见 [experiments](../experiments/)。

## 当前版本导读

当前方案强调模型生成建议时提出复查问题，并把问题、证据需求和责任角色保存为可跨事件继续处理的任务。第四轮在相同资料权限和调用上限下，对比“直接取证／显式条件演练”与“仅当前事件／持续保存”四种组合。表中百分比是每组1152次事件处理中，三个角色均正确且有已见证据支持的比例。

多角色协作主要发生在问题关联责任角色、共享真实证据、分别更新资格／行动／报告结论三个环节。当前原型由同一模型依次承担三个角色；第四轮固定调用三个角色，隔离取证与任务保存的影响。

以下JSON示例与反例回执说明记录的是第三轮实现。第四轮的持续任务结构和结果见[实验说明](../experiments/04-persistent-probes/README.md)及[冻结实现](../experiments/04-persistent-probes/source/engine.mjs)。

## 1. 一句话说，这个方案想解决什么问题？

让智能体在条件变化后，主动检查已经保存、仍被使用的旧建议：**寻找能推翻旧结论的具体条件，把它转成取证任务，再由相应角色依据真实资料更新记忆。**

例如，系统此前判断某人不符合岗位条件，建议撤回申请。后来每周排班出现“1天或3天”两种候选；其中3天已经可能符合新规则。系统需要发现这条旧建议可能失效，读取排班确认，再分别更新资格、行动和报告。

## 2. 什么是“记忆探针”？为什么叫探针？

“探针”指一个针对旧结论适用边界的主动检查机制。它像一个定向检测器：选定目标记忆，测试某个来源允许的条件是否足以改变结论，并给出下一步需要检查的资料。

它的输出需要足够具体，能够交给程序执行，例如：“在每周3天、每天12小时、申请仍在途时，旧的撤回建议应变成等待；请读取排班核定档案。”因此，“探针”既包含模型提出的条件反例，也包含将这个反例落实为取证和复核任务的执行协议。

第三轮实现把反例搜索安排在相关条件变化后；每次任务都绑定当时的记忆和来源版本。

## 3. 探针和记忆是什么关系？是不是又存了一份答案？

两者承担不同职责：记忆保存当前业务结论，探针检查该结论是否仍适用。

| 对象 | 保存什么 | 在流程中的用途 |
|---|---|---|
| 当前记忆 | 目标角色、字段值、确定性状态、版本、引用和历史说明 | 为后续任务提供当前建议 |
| 反例 | 来源允许的条件、该条件下的替代结论、引用 | 指出旧结论可能在哪个条件下失效 |
| 取证与复核任务 | 目标版本、事实版本、规则ID、拟读取资料、任务状态 | 调度真实取证和角色复核 |
| 审计回执 | 实际读取、假设确认或排除、角色提交及证据一致性 | 解释本次复核实际完成了什么 |

反例中的替代值不会直接覆盖当前记忆。正式写入来自后续角色对真实证据的判断。参见 [状态与执行逻辑](../runtime/engine.mjs)。

## 4. 模型实际输出的探针长什么样？

模型输出的是一个受约束的 JSON 请求，顶层为 `answer`、`witnesses`、`readIds`。下面保留真实案例中的 `match` 分支；原响应还包含行动和报告两个分支。

```json
{
  "answer": "每周3天、每天12小时满足当前规则，可以推翻旧的资格不符结论；需要读取排班确认。",
  "witnesses": [
    {
      "target": "match",
      "assumptions": {"days": 3, "hours": 12, "applied": true},
      "alternativeValues": {"eligible": true},
      "refs": ["d-4ae708c62fd8", "e-1cc9bed0463c"]
    }
  ],
  "readIds": ["d-b9f301e4a429"]
}
```

这里的说明文字为便于阅读的改写，字段和值对应已保存案例。模型选择目标、反例条件、替代值和档案；`refs` 必须包含当前规则，并来自实际可见来源。

完整原响应见 [该轨迹的 probe.json](../experiments/03-active-evidence/trajectories/t-d907d0469333/probe.json)，事件为 `e-1cc9bed0463c`；结构约束见 [prompts.mjs](../runtime/prompts.mjs)。

## 5. 模型 JSON、程序任务和审计回执为什么分成三层？

三层分别回答“模型提出什么”“系统执行什么”“执行结果如何”。版本号与任务状态由程序填写，读者可以清楚区分模型判断和控制器记录。

**第一层：模型请求。** 即上一问中的 `witnesses` 与 `readIds`。

**第二层：控制器生成的任务。** 同一案例的关键字段如下；程序另保存任务哈希 `id` 和上下文哈希 `stamp`。

```json
{
  "target": "match",
  "ruleId": "d-4ae708c62fd8",
  "targetVersion": 3,
  "factVersions": {"days": 2, "hours": 2, "applied": 2},
  "assumptions": {"days": 3, "hours": 12, "applied": true},
  "claimedAlternativeValues": {"eligible": true},
  "requestedDocumentIds": ["d-b9f301e4a429"],
  "status": "pending",
  "kind": "counterexample-evidence-obligation",
  "notFact": true,
  "notSemanticProof": true
}
```

**第三层：离线审计回执。** 对同一任务，审计记录包含：

```json
{
  "target": "match",
  "hostStatus": "local-review-completed",
  "actuallyReadIds": ["d-b9f301e4a429"],
  "requestedEvidenceReadCompleted": true,
  "assumptionResolutionFromActualFacts": "confirmed",
  "localReviewCommitted": true,
  "finalTargetEvidenceAligned": true
}
```

第二层任务由运行时建立并更新；第三层详细回执由 [支持性审计程序](../runtime/support.py) 根据已保存记录计算，结果见 [evidence-support-audit.json](../experiments/03-active-evidence/evidence-support-audit.json)。

## 6. 探针具体如何绑定一条长期记忆？

当前记忆以角色ID标识，例如 `match`、`path`、`report`；每次成功提交递增记忆版本。任务记录 `target` 和 `targetVersion`，同时记录当前 `ruleId`、各事实的 `factVersions`，并计算上下文指纹 `stamp`。

这样，一项复核请求能够追溯到：“针对第3版资格记忆，在第2版排班事实和指定岗位规则下产生。”角色写入后，任务继续记录 `newTargetVersion`。

当前任务在同一事件内完成处理并保存日志；失败的角色进入后续待处理列表。跨事件持续追踪未解决的取证任务，是下一阶段要扩展的任务管理能力。

## 7. 什么变化会触发探针？是每次聊天都搜索反例吗？

当前控制器先检查来源作用域与事实变化，再按声明依赖安排候选角色：排班天数、工时或规则变化涉及三个角色；申请状态变化主要涉及行动角色。无相关变化时直接保留状态。

对存在相关候选、且来源提供2—4个有限可能世界的事件，增强组获得一次额外调用。探针只寻找能够推翻“当前已确定结论”的反例；目标为 `null/uncertain` 时，由普通复核继续处理不确定性。

开放未知条件没有穷尽候选时，当前实现走普通规划与角色判断。这个边界使“已列出的候选条件”与“尚未掌握的可能条件”保持明确区分。

## 8. 这里的“演练未来”到底演练了什么？

演练的是条件成立时的结论变化。例如在真实来源允许的两个排班候选中，分别考虑“每周1天”和“每周3天”会产生什么资格与行动。

当前版本采用**反例搜索**：找到一个合法条件，使目标结论与旧记忆不同，即可提出复核任务。它不要求模型给未来事件分配概率，也不预测用户最后一定采用哪个排班。最终采用哪种条件，需要通过确认档案或新的实际观测确定。

## 9. 如何防止把模型假设当成真实事实？

执行链把假设和事实放在不同通道：

1. 模型只能从当前来源允许的 `worlds` 中选取反例条件。
2. 控制器检查目标、字段类型、规则引用及条件是否属于允许集合。
3. 反例和替代值只进入任务记录；后续普通角色提示不接收该原始反例请求。
4. 真正的 `facts` 只由当前作用域的来源观测更新。
5. 正式角色基于更新后的事实与原件独立提交结论。

控制器负责这些结构约束；反例计算是否正确由实验中的独立程序审计。本轮46条已提出反例均通过语义核验。

## 10. 如果没有反例、取证失败，或者读到的资料排除了反例，会怎样？

没有反例时，普通规划继续执行；探针不会因此删除候选角色。可选探针步骤发生格式、引用等错误时，也继续普通流程，并保留该次错误与调用成本。

取证排除反例同样有价值。例如反例需要每周3天，而真实确认只有1天，系统就有依据重新评估旧建议。当前回执区分 `confirmed`、`refuted` 和 `unresolved`。其中 `local-review-completed` 只表示角色完成了一次合法提交；证据是否解决不确定性另行记录。

本轮46项探针任务中，15项假设被确认、16项被排除，另15项保持未解决；这些数目按目标任务计数。

## 11. 探针和记忆会怎样出现在上下文里？

探针阶段接收当前事件、事实及候选域、规则原文、目标记忆、已读来源和可检索目录。目录仅提供ID、标题和作用域；读取之后，原文才加入 `sources`。

普通角色阶段继续接收当前事实和原文，旧记忆说明放入 `historicalExplanation`，同时标出生成版本与引用。这样，旧解释仍可供追踪，却不会被包装成本轮新观测。

| 阶段 | 主要上下文 | 输出用途 |
|---|---|---|
| 探针搜索 | 旧目标、当前事实、允许条件、规则、档案目录 | 形成反例与取证请求 |
| 普通规划 | 真实取证后的事实与来源、候选角色 | 选择后续读取与角色任务 |
| 角色复核 | 当前事实与原件、指定目标、历史说明 | 写入该角色的新结论 |
| 离线审计 | 保存的来源、版本、调用和状态 | 计算正确性、支持性与任务完成情况 |

## 12. 既然资格规则可以计算，为什么还需要大模型？

在当前阈值任务中，规则程序可以算出参考答案，因此实验能对模型的分支计算作精确检查。这里保留大模型，是为了检验它能否完成从旧建议到反例、档案选择和角色判断的整条过程。

实际应用还会面对自然语言建议、分散来源、隐含条件和不一致表述，大模型的潜在价值在于把这些材料组织成可执行复核请求。工程上适合分工：确定的算术与类型交给程序，语义解释与资料选择交给模型。下一步将加入符号规则对照，检验哪些环节需要模型、哪些环节适合直接验证。

## 13. 它与普通自检、RAG或记忆更新工具有什么区别？

| 机制 | 主要关注点 | 与本方案的连接 |
|---|---|---|
| 普通自检 | 再检查回答是否合理 | 本项目将同预算的自由额外复核作为强对照 |
| RAG检索 | 为当前问题获取相关资料 | 探针提出一个具体的旧结论失效条件，据此请求核定资料 |
| 记忆更新工具 | 找到记忆并修改内容或元数据 | 探针提供更新前的取证理由、目标版本和角色任务 |
| 反例取证探针 | 哪个允许条件能推翻哪条旧结论，应取什么证据 | 将判断转成可执行任务，并区分读取、复核与假设解决 |

这些能力可以组合使用。探针可以置于已有检索与记忆存储工具之上，负责安排“为什么现在需要核查这一条”。

## 14. 多智能体体现在哪里？目前有多少个真正独立的角色？

原型有三个明确分工的模型角色：资格角色维护 `eligible`，行动角色维护 `next`，报告角色维护 `recommend`。每个被调度的角色都执行真实模型调用，并单独提交自己的记忆字段。

当前由一个控制器顺序调度，同一模型承担三个角色。来源变化可以使一个或多个角色需要重算，已更新的状态继续进入后续事件。因此，本轮重点测量的是**多角色依赖维护与连续状态传播**。面向不同模型、并发执行和多个写入者的扩展，需要增加任务锁与版本冲突处理。

## 15. 完整对照实验究竟显示了什么收益？

最新连续事件实验包含12条轨迹、每条6个事件。三组都保留自身连续状态，每事件最多5次调用、读取一份档案；各独立策略成本均计入完整初始化。

| 方案 | 全部角色正确 | 正确且证据充分 | 角色复核调用 | 读档次数 | 独立策略总token |
|---|---:|---:|---:|---:|---:|
| 普通流程 | 52/72 | 49/72 | 106 | 6 | 390,248 |
| 普通额外复核 | 66/72 | 66/72 | 138 | 12 | 520,048 |
| 反例取证探针 | 64/72 | 64/72 | 117 | 11 | 487,240 |

相较普通流程，探针组多正确12个事件，并将正确且证据充分的事件增加15个。相较普通额外复核，探针少21次角色调用、少6.3%总token，对应少正确2个事件；这是本轮观察到的质量与成本选择。

31次搜索提出46条成立反例；按已执行搜索中的可反驳目标计算，56个机会中捕获46个。11次真实读取服务31条目标任务，一个档案可以同时支持三个角色。完整数据见 [主统计](../experiments/03-active-evidence/summary.json) 和 [独立审计](../experiments/03-active-evidence/independent-audit.json)。

## 16. 为什么专门设置“普通额外复核”？接下来要超过什么标准？

它帮助回答一个关键问题：收益来自反例机制，还是来自多给模型一次思考和取证机会？普通额外复核与探针接收相同资料及候选世界，都能增加角色复核、请求一份档案，额外调用上限相同。

当前两组有一项机制差别：探针需要提出合法反例才能在额外阶段请求档案；自由复核可以直接请求。因此比较对象是完整取证策略。

下一阶段的目标是，在实际成本接近时提高正确率，或者维持同等正确率并减少调用、读取与token。主要改进方向是降低反例漏检：本轮有3次空搜索遗漏了可成立反例，部分旧错误随后沿事件序列保留。

## 17. GPT与DeepSeek的联合实验说明了什么？

早期同题实验使用 `gpt-6.1-sol / medium / 8192` 与 `deepseek-flash / 关闭推理 / 1100`。每模型每组54格，题目、上下文预算和回读权限相同，推理配置不同。

| 组别 | DeepSeek生成／主评审 | GPT生成／主评审 | DeepSeek生成／GPT复核 | GPT生成／GPT复核 |
|---|---:|---:|---:|---:|
| 原协议＋自由探针 | 2/54 | 13/54 | 2/54 | 13/54 |
| 明确接口＋静态卡 | 29/54 | 42/54 | 18/54 | 33/54 |
| 明确接口＋自由探针 | 29/54 | 43/54 | 12/54 | 39/54 |
| 明确接口＋条件探针 | 31/54 | 43/54 | 16/54 | 40/54 |

主评审为DeepSeek，后两列保留GPT复核结果。保持自由探针不变时，接口修正使两模型主评审通过数分别从2提升至29、从13提升至43。它确立了共同工程基础：先把状态、动作和引用边界定义清楚，再检验探针的增量。条件探针相对静态卡的改善较小且随评审变化，后续因而转向可程序核对的连续取证实验。

完整记录见 [双模型实验目录](../experiments/01-cross-model/)。

## 18. 为什么还做了一轮“说明先行”的提交实验？

前期发现模型可能在正文中得出正确结论，却把旧值写回结构字段。为解决这个基础问题，单独比较了JSON示例键序与额外提交复核。

| 方案 | 新72例正确数 | 已见24例回归 | 全96例独立策略总token |
|---|---:|---:|---:|
| 原提交顺序 | 66/72 | 20/24 | 290,435 |
| 说明先行 | 70/72 | 24/24 | 289,863 |
| 额外提交复核 | 71/72 | 23/24 | 573,481 |

说明先行修复5个新例，也改坏1个新例，token基本持平；额外复核成本接近翻倍。这一结果支持把更稳定的提交格式设为后续各组的共同基础。详见 [提交一致性实验](../experiments/02-commit-consistency/)。

## 19. 上下文压缩会怎样影响探针？磁盘重读验证了什么？

设计上，把目标版本、来源引用、事实版本与未完成任务保存为独立结构数据，压缩后按需重新载入；原文不足时再检索。摘要主要帮助定位，正式复核仍需要实际证据。

最新连续事件实验在第四个事件前从磁盘重新读取状态，检验持久化后的事实、记忆版本和后续执行能否衔接。这项检查覆盖的是**状态保存与恢复**。

早期双模型实验还比较了宽、紧两档上下文，并在压缩后重载探针元数据和允许的原文。进一步的压缩实验将单独控制压缩率、原文丢失、摘要误写及任务恢复，观察哪些信息必须可靠保存。

## 20. 核心原创点是什么？下一步怎样把原型变成更有用的插件？

核心设计是把“旧记忆可能失效”落实成一套可执行协议：**来源约束的反例 → 绑定版本的取证任务 → 指定角色复核 → 分层完成回执**。模型探索条件变化，控制器管理真实证据、任务与写入边界，实验分别检验反例成立、取证效果和最终建议。

项目吸收了现有记忆管理、依赖维护、反事实验证和工具反馈研究的思路；与Mem0、Letta等产品的联系及研究资料见 [README中的产品与研究比较](../README.md#与现有产品的差异化)。本项目将创新落在上述协议组合、执行细节和对照验证上。

接下来优先推进四项工作：

1. **提高反例召回。** 对关键阈值增加便宜的程序检查，并与自由额外复核保持完整对照。
2. **从自然语言建立绑定。** 将目前提供的规范化观测和声明依赖，扩展为模型从原始材料提取，再核对引用与范围。
3. **持续管理未完成任务。** 区分已读取、已提交、仍未知，支持跨事件恢复和版本冲突处理。
4. **接入真实记忆工具。** 在记忆写入后登记依赖，在后续事件进入时筛选相关目标，再通过现有检索与写入接口执行局部复核。

答辩时可以这样概括：**我们已经把反例推理转成了可执行、可追踪的记忆维护任务，并通过对照实验找到它相对普通流程的收益及与额外复核之间的成本选择。下一步重点是扩大自然语言适用范围、提高反例召回，并保持清晰的证据与版本管理。**
